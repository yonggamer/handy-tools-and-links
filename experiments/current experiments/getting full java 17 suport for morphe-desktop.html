Getting Full Java 17 Support for Morphe Desktop

Investigating and improving Java 17 compatibility for Morphe Desktop, with a focus on getting both the graphical interface and command-line interface working across different Java architectures.

⚠ Partially supported

📖 About this experiment

This experiment investigates the current Java 17 compatibility of Morphe Desktop.

The main objective is to achieve full Java 17 compatibility for both 64-bit and 32-bit Java Runtime Environments (JREs).

At the moment, Java 17 support is only partial overall. The 64-bit JRE works with both the graphical user interface (GUI) and the command-line interface (CLI), while the 32-bit JRE currently only works with the CLI.

During the investigation, a major limitation was identified in the native graphics dependency: the Windows x86 Skiko runtime needed by the GUI was not available in the runtime configuration examined.

💡 How the discovery was made

The reason why the 32-bit graphical interface did not work was not immediately obvious. Simply looking at the Java version or the platform detector did not explain the problem.

The breakthrough came from investigating how Morphe Desktop handles architecture compatibility in its native dependencies.

1. The original attempt

The initial objective was to add x86 (32-bit) support to Morphe Desktop so that the GUI could also run with a 32-bit Java 17 runtime.

2. Investigating the four files

The changes in pull request #399 provided a way to understand how architecture support is implemented throughout the project.

Instead of only examining platform detection, the investigation also covered dependency declarations, native runtime hashes and bootstrap verification tests.

3. Comparing the supported architectures

The ARM64 changes showed that adding support for a new architecture involves more than adding an architecture name to the platform detector.

The appropriate Compose Desktop dependency, native Skiko runtime and bootstrap verification information must also be available.

4. Finding the missing x86 Skiko runtime

When attempting to add x86 to the relevant files, the investigation reached an important limitation: there was no corresponding Windows x86 Skiko runtime available in the runtime configuration being investigated.

This was the missing piece that explained why adding x86 to the platform definitions alone would not make the graphical interface work.

🔎 The key discovery

The problem was not simply that Morphe Desktop did not recognise a 32-bit Java runtime. The GUI also depended on native graphics components, and the required Windows x86 Skiko runtime was missing from the available dependency configuration.

⚙️ Why 32-bit GUI support does not work

Morphe Desktop uses Compose Desktop for its graphical interface. Compose Desktop relies on Skiko for native graphics integration.

Skiko is not just an ordinary Java library. It also needs native platform-specific binaries that match the operating system and processor architecture.

Java alone is not enough

A 32-bit Java runtime can execute compatible Java bytecode. However, that does not mean every native library required by the application is available for 32-bit Windows.

The missing native runtime

The Windows x86 GUI needs a compatible native Skiko runtime. Without that runtime, the graphics dependency cannot be loaded in the required architecture.

Adding x86 to PlatformDetector.kt would only allow the application to identify the architecture. It would not supply the missing native graphics binaries.

Why the CLI still works

The command-line interface does not need to initialize the same graphical rendering stack. It can therefore work with 32-bit Java even when the GUI cannot initialize its native graphics dependencies.

Why the four files matter

  • PlatformDetector.kt identifies the operating system and architecture.
  • libs.versions.toml defines the required dependency versions and platform libraries.
  • GenerateBootstrapConstantsTask.java generates the native runtime verification information.
  • BootstrapDownloaderVerificationTest.kt checks important bootstrap and native dependency behaviour.
Important distinction

Platform detection, dependency availability and native runtime compatibility are three separate requirements. All of them must work together before the GUI can run.

🖥️ Understanding the architectures

It is important not to confuse x86, x64 and ARM64. They are different processor architectures and require compatible native binaries.

Architecture Bits Description
x86 32-bit Traditional 32-bit Intel-compatible architecture.
x64 64-bit 64-bit extension of the x86 architecture.
ARM64 64-bit 64-bit ARM architecture.

Windows ARM64 support does not automatically provide Windows x86 support. Each architecture needs the appropriate native dependencies.

📦 Skiko – Native graphics dependency

Skiko is an important part of the investigation because it provides the native graphics integration used by Compose Desktop.

Its native runtime artifacts are architecture- specific. This means the application cannot simply use an x64 or ARM64 native binary as a replacement for a Windows x86 runtime.

JetBrains Skiko – GitHub Official Skiko source repository and project information. ↗

Why this repository is important

  • It provides the source code and project information for Skiko.
  • It helps investigate the available native graphics implementations.
  • Its releases and dependency artifacts are relevant when checking architecture support.
  • It provides a reference for determining whether a suitable x86 runtime is available.

The absence of a suitable x86 runtime in the configuration examined is the limitation identified by this experiment. It should not be interpreted as proof that no x86 Skiko binaries have ever existed in any release or third-party build.

🧪 Current experimental test: Building a 32-bit Skiko runtime

Although the investigation identified the missing Windows x86 Skiko runtime as the main limitation, I am currently testing whether this limitation can be overcome.

On my own fork of Skiko, I am experimenting with building a 32-bit version of skiko-awt-runtime. The purpose is to determine whether a compatible native graphics runtime can be produced and used by Morphe Desktop with a 32-bit Java 17 runtime.

Current test objective

Build a Windows x86 skiko-awt-runtime and integrate it into Morphe Desktop to test whether the complete graphical interface can run with Java 17 (32-bit).

What I am trying to establish

  • Whether Skiko can be built successfully for Windows x86.
  • Whether the resulting native runtime can be loaded by a 32-bit Java 17 runtime.
  • Whether Compose Desktop can initialize its graphical components using that runtime.
  • Whether Morphe Desktop can achieve full GUI and CLI compatibility with 32-bit Java 17.

Why this test matters

The missing runtime identified during the investigation may be a dependency availability limitation rather than an absolute technical impossibility.

By attempting to build the runtime independently, I can investigate whether the required native graphics support can be created instead of relying on an already published runtime artifact.

Current test status

Experimental – testing in progress

Full 32-bit GUI compatibility has not yet been confirmed. The result of this experiment will determine whether the custom runtime can make full Java 17 support possible.

💻 Findings from the current source code

1. PlatformDetector.kt

The investigated platform configuration recognizes x64 and ARM64 architectures. It does not explicitly recognize x86/32-bit architecture.

2. GenerateBootstrapConstantsTask.java

The bootstrap generation task creates SHA-256 hashes for native dependencies and Skiko runtime artifacts for six platform targets: macOS x64, macOS ARM64, Linux x64, Linux ARM64, Windows x64 and Windows ARM64.

3. libs.versions.toml

This file defines dependency versions, including Compose Desktop and other libraries. It is important to check whether the selected dependency versions and available native artifacts support the intended Java architecture.

4. BootstrapDownloaderVerificationTest.kt

The existing tests verify that bootstrap constants are generated, hashes have the expected format, and Skiko/Skia classes can be loaded. They also check OSHI initialization.

These tests do not establish that the 32-bit graphical interface works. Additional architecture-specific testing would be needed.
